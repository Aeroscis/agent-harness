# program-project-doc — 软件工程文档写作规范

写软件工程文档的目标只有一个：**让读者用最少的猜测理解系统**。
凡是需要读者"翻译"的词，都是坏词。

## 一、禁用词表

以下词汇**一律不许出现在文档正文**。它们要么是靠比喻才能理解的行话，要么含义含糊、随语境漂移。用户逐批补充过不喜欢的新词，此表持续更新。**命中即改写**：发现禁用词时不是删掉，而是追问它到底指什么，换成右列的具体说法。

| 禁用 | 问题 | 按语境替换为 |
|---|---|---|
| 门面 | 比喻，看不出是"对外接口"还是"入口"还是"简化封装" | 对外接口 / 公开 API / 入口 / 统一封装层（说清是哪种） |
| 冒烟 | 黑话，看不出测了什么、测到什么程度 | 基本可用性验证 / 快速回归检查（并写明验证了哪几条） |
| 基线 | 一词多义：基准版本？性能基准？对照组？ | 参照版本 vX.Y / 性能基准 / 当前实现（用哪个写哪个） |
| 接线 | 比喻，看不出是注入依赖、注册回调还是连配置 | 注入依赖 / 注册 / 调用 / 把 A 传给 B（写清具体动作） |
| 落盘 | 口语，看不出写到哪、什么格式、是否同步 | 写入文件 / 保存到 `<路径>`（尽量给出路径和格式） |
| 流血 | 比喻且语义混乱（报错？持续失败？性能下降？） | 报错 / 失败 / 抛出异常 / 指标下降（说清具体现象） |
| 全部收到 XX 里 | 看不出是写入、归档还是注册 | 写明具体动作：全部写入 `XX` / 全部注册到 `XX` / 全部由 `XX` 保管 |
| 废弃 | 没说清是谁停用、被什么取代 | 已停止使用 / 已被 `X` 取代（写明替代物和迁移办法） |
| 语义 | 一词多义：词义？行为？预期效果？ | 含义 / 行为 / 预期效果（写清指哪一个） |
| 装配 | 比喻，看不出是配置、组装还是初始化 | 配置（指定替换词，不要换成别的比喻） |
| 命中 | 看不出匹配了什么、匹配到什么程度 | 匹配到 / 找到 / 覆盖到（写明对象，如"匹配到规则 R3"） |
| 原语 | 译名黑话，字面推不出含义 | 唯一的底层接口，其余功能均由它组合而成 / 最小调用单位（点明唯一性和组合关系；不要只写"基础操作"这种还是含糊的说法） |
| 缺省 | 生僻旧译，部分读者不认识 | 默认 |
| 钩子 | 比喻，看不出是回调、扩展点还是触发时机 | 回调 / 扩展点 / 触发时机（说清机制）；Git hooks、React Hooks 这类专名直接写英文原词 |
| 缺口 | 比喻，看不出缺什么、差多少 | 写明缺的东西：未实现的功能 / 未覆盖的场景 / 与 `X` 的差距（给数字） |
| 收尾 | 口语，看不出包含哪些步骤 | 列出结束前的具体步骤：关闭句柄、释放资源、发送完成事件 |
| 裁剪 | 比喻，看不出删了什么、删到什么程度 | 删除 / 精简（写明删了哪些、保留哪些）；图片的字面裁剪除外 |
| 驱动 | "X 驱动的 Y"看不出因果方向 | 由 X 触发 / 基于 X / 以 X 为输入（写清因果关系） |
| 门禁 | 比喻，看不出是哪些检查、挡住什么动作 | 合并前必须通过的检查 / 失败时阻止合并的验证步骤（列明检查项和被阻止的动作）；安防领域的字面门禁系统除外 |
| 地基 | 比喻，看不出是基础依赖、核心模块还是底层抽象 | 写明具体是什么：运行所需的依赖 / 其余模块构建于其上的核心模块 / 底层接口（说清指哪种）；建筑领域的字面地基除外 |

**处理流程**：写完文档后自查一遍词表（可 grep）。发现禁用词时不是删掉，而是**追问它到底指什么**，换成表中右列的具体说法；若语境特殊、右列都不贴切，和用户讨论后再定措辞，不许换个比喻继续糊弄。

## 二、禁用词推广原则

词表只是起点。判断任何一个词该不该用的标准：

1. **字面可解码**：第一次接触的读者，不看上下文能否从字面推出含义？推不出就换说法。
2. **单义性**：这个词在文档里是否只指一个东西？一词多义就在首次出现处定义，或换两个不同的词。
3. **动词优先**：少造名词黑话，多写"谁对谁做了什么"。`A 在启动时读取配置并注册到 B` 永远好于 `A 完成配置装配`。
4. **比喻是负债**：pipeline 叫"流水线"、守护进程叫"看门狗"这类行业通用词可以用；自己新发明的比喻一律不许用。
5. **不许空转**：`赋能`、`打通`、`闭环`、`抓手`、`沉淀`、`拉齐` 这类大厂黑话同样禁用，必须写成具体动作和结果。

## 三、按读者分层：用户文档与设计文档分开写
- **动笔前先问：这篇给谁看？** 用户（黑箱视角：装、用、配、排错）还是维护者（白箱视角：架构、取舍、内部实现）？一篇文档只服务一类读者，不许两边内容混写。
- **仓库根目录是用户的领地**：README 等入口文档必须是黑箱内容——功能、安装、用法、配置、已知问题。内部实现、模块划分、设计取舍一律不写。
- **设计内容只给链接，不搬正文**：用户文档确需设计背景时，链接到设计文档并标注"内部设计文档，与使用无关"，让用户知道这是可选深入。
- **黑箱写法**：描述行为——输入、输出、副作用、错误情况；不描述实现路径。用户问"它做了什么"，维护者文档才回答"它怎么做到的"。
- **写能力，不写身份**：开头和用户可见段落写读者能用它做什么，不写它是什么角色、注册了什么、内部含哪些组件。判例：`seam 注册 ctx.x 并追加 x/event 记录` 是身份叙述；`你可以给每条消息存一条笔记，重启后还在` 是能力描述。

## 四、其他行文要求

- **术语全文统一**：同一个组件/概念全篇只用一个名字；别名可以在首次出现时用括号注明，之后不许混用。
- **首次出现先定义**：缩写、专有名词第一次出现时给全称或一句解释。
- **名词带锚点**：提到文件、函数、配置项时，尽量给路径或标识符（`src/auth/token.ts` 的 `refresh()`），而不是"那个模块"。
- **数字要可核验**：写性能、规模、版本号时必须给测量口径或来源；给不出就删掉这个数字，不许写"显著提升"这类空话。
- **删掉无信息量的修饰**：`强大的`、`灵活的`、`优雅的`、`业界领先的` 一律删除，用事实代替。
- **一句话一个意思**：长句拆短；一个段落只讲一个主题，主题变化就开新段。
- **结构服务于查找**：标题层级不超过三层；每节开头第一句先给结论，再给细节。
- **标题有的放矢**：标题点明本节的主题（安装、配置、组件列表、已知问题），读者扫目录就能定位。禁用两类坏标题：元叙述式——`一句话总结`、`这个库建立在两个想法之上`、`盒子里有什么`，读者不读完正文不知道这节讲什么，标题成了悬念而不是索引；比喻式——目录里搜"组件列表"搜不到"盒子里有什么"。标题也不加括号补充解释：正文本身就是对标题的解释，需要强调就在正文里写并加粗，括号是想解释什么就说明这个标题没说清。
- **代码即文档**：能用一个 3 行的代码示例说明的用法，不要用三段文字描述。
- **不写易腐的度量**：代码行数、文件个数这类随迭代立刻过期的数字不写。规模描述用稳定的说法（"数千行的单文件"而非"3218 行"），确需精确数字时给出版本号或日期口径。
- **不写中间过程**：文档只记录结果，不记录写作过程。AI 的思考过程、"X 时间已修改到 X 处"这类进度快照一律不进文档；唯一例外是文档本身声明为过程记录（如 MEMORY、工作日志），此时要在开头写明性质。
- **不写未来承诺**：正文只描述当前代码的行为。"将来会支持 X"这类未来时、迁移计划、未实现的规格一律不进稳态文档；未来计划和过程记录一样是专门的文档类型（路线图、TODO、设计提案），单独成文并在开头写明性质，从正文链接过去。历史证据同理，只放带日期的专门记录（变更日志、ADR）。
- **设计文档解释，不枚举**：设计内容写到概念层——整体设计、主要组件的架构、数据流概述——精确细节链接到代码。不许在文档里复述 API 全目录、全量字段表、事件载荷清单、JSDoc；读者需要精确细节时给他链接，不是给他抄本。
- **操作声明必须跑过**：文档要写某个命令、配置片段、默认值、报错行为，就必须先在当前代码上实际执行验证，只写观察到的输出、警告和失败。复现不了的声明删掉，不许凭记忆、类比或相邻包的 README 写操作行为；依赖没有的密钥或网络时，写明由谁负责验证，而不是断言行为。
- **删减不伤行为**：精简字数时，若删掉某句改变的是"承诺的行为"而不是"冗余的解释"，停下来先提出行为变更，不许靠删文档偷偷改契约。字数预算是护栏不是目标，不许为了字数删掉必须保留的契约（失败情况、限制、所有权）。
- **代码注释禁用 markdown 格式**：注释按所用语言的注释规范写，不许用 markdown 语法——`**加粗**`、`# 标题`、`- 列表`、反引号包裹 这类标记在注释里是纯噪音。注释用完整句子、缩进和空行组织结构，不用标记模拟格式；JSDoc/docstring 这类本身就是 markdown 方言的文档注释体系除外。

## 五、每篇文档有唯一草稿区

部分想法、未定方向、进行中的状态，只允许出现在文末一个明确标注"非权威"的区域（Dev Note），其余正文都是写完的当前状态。工作结束后把结论提升进正文、删掉草稿区的碎语，旧内容由 git 历史保存；草稿区不许变成第二个待办清单。

## 六、交付前自查清单

- [ ] grep 一遍禁用词表，正文无匹配（词表自身除外）
- [ ] 全文无自造比喻、无大厂黑话
- [ ] 每个术语全篇写法一致
- [ ] 每个数字有口径或来源
- [ ] 每节第一句是该节结论
- [ ] 本篇的目标读者明确，未混入另一类读者的内容；设计细节只以带标注的链接出现
- [ ] 无易腐度量（精确行数、文件数），无 AI 思考过程或修改进度快照（过程性文档除外）
- [ ] 无未来时和迁移计划混入正文（专门的路线图/提案文档除外）；文末草稿区标注了非权威
- [ ] 所有操作声明（命令、配置、默认值、报错）都实际执行验证过，复现不了的已删
- [ ] 新人测试：没有本仓库背景的工程师，跟着 3-5 个页面能否搞懂"它做什么、怎么安全地用、状态存哪、怎么失败、去哪改"？为搞懂公开流程被迫翻源码 = 缺解释该补；被迫读无关内部细节 = 该下移
- [ ] 标题全部有的放矢：扫目录能定位，无元叙述式标题（如"一句话总结"），无比喻式标题，无括号补充解释
- [ ] 精简字数时没有删掉承诺的行为（失败情况、限制、所有权）
- [ ] 代码注释里无 markdown 标记（`**`、`#` 列表号、反引号；JSDoc 等文档注释体系除外）
