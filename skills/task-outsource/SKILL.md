# task-outsource — 任务外包工坊

**你（付费、聪明）不亲自干活，只负责：判断 → 打包 → 出 prompt → 事后验收。**
把任务交给免费 API 会话执行，省钱。但**外包有隐藏成本**：写作业纸 + 验收都要花你的 token，
所以核心纪律是——**按复杂度打包，别过度打包；验收要硬证据，别信回报**。

## 第 0 步：先决定"该不该外包"

以下情况**绝不外包**，直接在当前会话做，并告诉用户原因：
- 敏感项目 / 含密钥 / 机密代码（免费会话 = 明文交给第三方，**隐私红灯**，必须先提醒用户）
- 需要全局架构设计、深层跨模块推理、牵一发动全身的高价值高风险改动
- 改坏代价极高、必须一遍过的任务
- 任务本身模糊，连意图都说不清（先问清楚再谈外包）

其余情况才往下走。

## 第 1 步：定档 —— 这是整个 skill 的核心判断

判断依据是**任务性质**，不是"目标模型有多笨"（你事前多半判断不准模型的真实智力）。

| 用哪档 | 触发条件（任务性质） | 作业纸风格 |
|---|---|---|
| **high** | 任务需要**探索/试错/局部决策**，但风险可控、不连锁爆炸。例：改一段逻辑、写个新函数、跨几个文件梳理后改动、选一个实现方案 | 给意图 + 约束 + 参考上下文；步骤宽松，留给执行者自己发现 |
| **low** | 任务**机械、模板化、容错低**，且边界清晰。例：批量替换、按固定模板生成、跑固定命令、照抄某处改到多处 | 给详细步骤 + 锚点 + 检查点；但保留基本判断空间，别锁死 |
| 都不用 | 该不该外包里列的情况 | 直接做，或问用户 |

**拿不准就默认 high**——大部分"省 token"的活其实属于 high；low 只留给真正机械重复的。

## 第 2 步：收集压缩版工程上下文（两档通用）

只给"入口"，不替执行者穷举内容（低档可以稍多一点锚点，但别过度）：
- 项目根目录绝对路径
- **相关文件/目录绝对路径 + 一句话作用**（让它自己打开读）
- 技术栈 / 代码风格约定（只写和本任务相关的）
- 构建/测试/运行命令（含 working directory）
- 已知的坑（有才写，别编）
- **敏感内容检查**：上下文里若含密钥/机密 → 回到第 0 步，提醒用户别外包

## 第 3 步：写作业纸 MD 到临时文件夹

路径：系统临时目录（Windows 用 `$env:TEMP`，macOS/Linux 用 `$TMPDIR`，取不到时回退 `/tmp`）下建一个子目录 `agent-task-outsource\`，文件名 `<任务英文名>.md`。

**打包纪律（重要）**：作业纸的详细度 = 任务复杂度决定，不是"越详细越好"。
- 极简任务（改一行、删一个文件）：作业纸可以只有几行，**别为它写八段**。
- 中复杂度：给步骤 + 锚点。
- 复杂但符合外包条件：给意图 + 约束 + 建议方向，细节留给执行者。

### 高档（high）模板

```markdown
# 任务：<标题>

## 目标（结果导向）
<要达成什么、为什么、做成什么样算好>

## 工程上下文（够用就好）
- 项目根目录：<绝对路径>
- 相关文件/目录（自己打开读）：
  - <绝对路径> —— <作用>
  - <绝对路径> —— <作用>
- 技术栈/约定：<只写相关的>
- 常用命令：<npm run build（项目根目录）>

## 约束 / 红线（写死，不许越）
- <例：不许改 package.json、不许动 src/auth、不许引入新依赖>

## 建议方向（可选，仅供参考，不强制）
<你猜的路径，注明"以你实际调研为准">

## 验收标准（可机器检查）
- [ ] <可 grep / 可跑 / 可看，别写"感觉不错">

## 完成汇报格式
1. 实际做了什么（方案）
2. 改了哪些文件 + 每处一句话摘要
3. 验证命令输出
4. 遇到目标/约束没覆盖的情况及你的判断
```

### 低档（low）模板

```markdown
# 任务：<标题>

## 目标
<可验证完成标准>

## 工程上下文（压缩版）
- 项目根目录：<绝对路径>
- 相关文件（自己打开读）：
  - <绝对路径> —— <作用>
- 技术栈/约定：<相关的>
- 常用命令：<含 working directory>

## 红线（绝对不能做；越线前停下汇报）
- <例：不许改 package.json>

## 执行步骤（每步带"怎么做 + 怎么验证"）
### 步骤 1：读取文件
- 打开 <绝对路径>，确认存在能读；读不到就停下原样汇报。

### 步骤 2：定位并替换
- 找下面这段（一字不差，给够上下文唯一）：
  ```
  <锚点>
  ```
- 替换为：
  ```
  <新文>
  ```
- 找不到锚点或拿不准：停下，把看到的情况原样汇报，别硬改。

### 步骤 3：运行验证命令
- 在 <working directory> 跑：`<完整命令>`
- 期望输出：<关键输出>
- 报错就做**小范围合理修复**（只修相关的）；修不动就停下汇报。

## 验收清单
- [ ] <可检查项>

## 完成汇报格式
1. 改了哪些文件 + 每处一句话摘要
2. 验证命令输出
3. 有没有"作业纸没写的情况"：有则描述你的判断/处理，无则写"无"
```

## 第 4 步：生成可复制 prompt

MD 全文内嵌，套执行指令，整体放 fenced code block。指令按档位微调。

高档版：
````markdown
你是一名有经验的工程师。下面是任务：给了目标和约束，没给每一步剧本——有些细节要你动手读代码、跑命令、试错，自己判断。

任务说明：
<粘贴 MD 全文>

执行要求：
1. 先通读目标，想清大致方案再动手。
2. 动手时主动探索（读文件、跑命令、看输出），用实际情况校准方案。
3. 严守红线；红线外实现细节你自己判断。
4. 遇到目标歧义/所需信息不存在且无法合理达成/会明显越红线：停下来如实汇报，别硬编绕过。
5. 做完按验收标准自查，不满足就修到满足（只修相关的）。
6. 按汇报格式逐条汇报，如实说明判断和取舍。
````

低档版：
````markdown
你是一名执行任务的工程师。作业纸已把步骤写得很详细，请照做。注意：作业纸是"详细引导"不是"锁死你"——没写死的合理细节可自己判断；但拿不准/没覆盖的地方，别瞎猜、别硬编、别绕过，先停下如实汇报。

任务作业纸：
<粘贴 MD 全文>

执行要求：
1. 先通读，尤其红线，再动手。
2. 按步骤一步步来；每步按验证方式检查，不对就停。
3. 严守红线，越线前先汇报。
4. 可在不越红线、不偏离目标前提下处理没写死的小细节；处理不了就汇报。
5. 做完按验收清单自查，不满足就修（只修相关的）。
6. 按汇报格式逐条汇报。
````

## 第 5 步：验收（硬证据，不是信回报）

用户把免费会话的回报贴回来时，别直接采信。要求或索取**可核验证据**：
- **改动证据**：让执行者回报里附 `git diff` / 具体改动行号，或让你抽查文件确认改动存在且正确。
- **验证证据**：让执行者附上验证命令的**真实输出**（不只是"成功了"），你检查关键行。
- **范围证据**：确认改动只出现在约定的文件里（可 grep / git status 核对）。
- 拿不准就**自己跑一遍验证命令**复核。

## 交付给用户
- 告诉用户：复制代码块内容，粘到免费 API 会话。
- 给 MD 文件绝对路径（留档/可改）。
- 提醒：免费会话做完后把**含证据的回报**贴回来，你负责验收。
- 若上下文含敏感内容：先提醒"这个不适合外包"，别直接打包。

## 小技巧
- **按复杂度缩放打包**，简单活别写八段——你的打包 token 也是成本。
- **验收标准写可机器检查的**（能 grep / 能跑 / 能看），别写主观词。
- **锚点给长不给短**（low 档尤其），带够上下文保证唯一。
- **红线宁多勿少**，并写"越线前先汇报"。
- **拿不准就默认 high**，low 只留给真正机械的活。
